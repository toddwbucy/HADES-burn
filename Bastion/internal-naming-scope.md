# Internal Naming Boundary: Scoping Document

Status: scope draft, 2026-06-11. Upstream of a PRD and Spec. No code moves until
both exist and a deployment window is scheduled.

## The ruling

Mythology is branding, function is naming. The application is named HADES and
its operator-facing surfaces carry that brand (binary name, crate names, env
prefix, systemd units, repo). Internal code, wire protocols, and data
structures are named by what they do. A module named `persephone` that holds
an extraction client tells a first-time reader nothing and invites a different
wrong guess from each reader. The naming scheme of the application must not
bleed into the internals.

The in-tree precedent: the training service (newest, PR #130) already uses the
functional proto package `hades.training`. The older extraction and embedding
protocols carry the legacy `persephone.*` packages. This change converges the
old code onto the convention the new code already follows.

## The keep list (branding layer, out of scope)

- Binary `hades`, crate names `hades-*`, workspace name
- Env prefix `HADES_*`, config paths `/etc/hades/`
- Systemd units `hades-daemon`, `hades-embedder`, `hades-extractor`, `hades-trainer`
- Repo name, the `olympus` workspace, sibling project names (Hermes, Hecate)
- Hermes keeps its product name. Its role changes under the bridge (the human
  window onto the forge-backed graph), but that is the bridge PRD's subject

## Blast-radius classes (these drive scheduling)

1. **Compile-only.** Module paths, internal types, test names. No runtime
   impact until a normal deploy. Can land any time the PR process allows.
2. **Wire-breaking.** Proto package renames change gRPC service paths.
   Requires a coordinated rebuild and restart of the extractor and trainer
   services plus the CLI. Must land in a scheduled quiet window: this is the
   class that cannot interrupt active WeaverTools work. Note the extractor
   unit is currently in a failed state anyway, and the trainer restart is
   already pending from PR #143, so one window can absorb all of it.
3. **Data.** Collection or database renames are migrations. The persephone_*
   collections are nearly empty (11 task docs total), so the migration is
   trivial IF the bridge work does not retire them first.
4. **Published-name.** PE-API is a contract name in documentation. The wire is
   OpenAI-style HTTP and does not carry the name, so this is a docs-and-comms
   change only.

## Sequencing: the bridge decides part of the rename

The forge-bridge direction (git issues/PRs as the work artifacts, HADES as the
index, Hermes as the human window) likely RETIRES the persephone task layer:
the task CRUD, the persephone_* collections, and possibly parts of the
provider protocol. Renaming a thing that is about to be deleted is wasted
motion and churn in the history.

Therefore:

1. **Bridge PRD first** (or at least its scope ruling): decide the fate of the
   task layer and the provider protocol.
2. **Naming PRD second**, covering the survivors. The service-client module
   rename (class 1) is bridge-independent and can be specified immediately.
3. **One deployment window** for everything in class 2 and 3, scheduled with
   the WeaverTools work in mind, and shared with the already-pending trainer
   restart from PR #143.

## Open decisions for the PRD

- Target name for the client module: one `service_clients` module vs split
  `clients::extraction` / `clients::embedding`.
- Proto strategy: rename packages in place (one breaking change, one window)
  vs freeze-and-supersede (new packages added, old ones removed after cutover).
  Given both consumers are in-tree, in-place is simpler.
- PE-API contract name: rename with alias, or keep.
- `bident_burn`: keep as operator-level name or fold into the bridge's store.
- Whether the daemon protocol docs ("Persephone provider protocol" phrasing in
  README and docs) get re-worded in the same PR or with the bridge work.

## What this is not

This is not a behavior change. Every rename is semantics-preserving, verified
by the existing test suite (43 CLI tests, 12 trainer tests, plus the
hades-core integration tests). The PRD should state this invariant and the
Spec should hold the renames to it.
